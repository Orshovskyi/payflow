# ADR-0005: Методика навантажувального експерименту

- Статус: Прийнято
- Дата: 2026-11-11

## Контекст
Щоб порівняння стратегій було коректним, прогони мають бути відтворюваними, ізольованими один від одного і
відбуватися в однакових умовах. Відрізнятися може лише механізм консистентності.

## Рішення

### Середовище
- Обидва сервіси працюють у контейнерах (`docker compose --profile app`) з однаковими лімітами: **2 CPU і 768 МБ**.
  PostgreSQL і Kafka мають по 2 CPU і 1 ГБ. Heap JVM задано відносно ліміту контейнера (`MaxRAMPercentage=75`).
- Один образ для всіх сервісів (`docker/service.Dockerfile`), шари Spring Boot, користувач без root.
- Стратегія та інтервал опитування outbox передаються змінними середовища (`STRATEGY`, `OUTBOX_POLL_INTERVAL`),
  тобто з одного й того самого образу.
- Gatling працює на хості, поза лімітами контейнерів, щоб генератор навантаження не конкурував із системою за CPU.

### Модель навантаження: відкрита
Перекази надходять із фіксованою інтенсивністю (`constantUsersPerSec`) незалежно від того, як швидко відповідає
система. Так поводиться реальний платіжний трафік. Відкрита модель також уникає coordinated omission:
у закритій моделі повільна система сама зменшувала б навантаження на себе, і затримки виглядали б кращими, ніж є.
Кожен віртуальний користувач надсилає один переказ між двома випадковими гаманцями зі 100.
Баланси великі (1 000 000), тож відмови через нестачу коштів практично неможливі, і обидві стратегії виконують
однакову роботу.

### Хід одного прогону (`experiments/run-experiment.sh`)
1. **Ізоляція:** `docker compose down -v`, тобто порожні БД, свіжий брокер Kafka, порожній Prometheus.
2. **Розігрів** (20 переказів/с, 20 с) — JIT, пули з'єднань, підключення consumer-груп. У замір не входить.
3. **Замір:** 10 с наростання навантаження + `durationSec` сталого навантаження.
4. **Злив:** очікування, доки жоден переказ не лишиться в `PENDING` (не довше 60 с).
5. **Збір:** `experiments/collect_results.py` пише `summary.json` і додає рядок у `experiments/results/summary.csv`.

### Джерела даних
| Показник | Джерело | Примітка |
|---|---|---|
| HTTP-затримка p50/p95/p99, пропускна здатність, помилки | Gatling (клієнт) | Точні значення. Пропускна здатність усереднена разом із фазою наростання |
| Наскрізна затримка саги p50/p95/p99 | Prometheus, гістограма `payflow_transfers_e2e_seconds` | Головна метрика порівняння; точність обмежена межами кошиків гістограми |
| Лаг outbox | Prometheus, `payflow_outbox_lag_seconds` | Лише для outbox |
| Кількість переказів за статусом, «зависли» в `PENDING` | БД | Точні; включають розігрів |
| Інваріант суми балансів | БД | Очікувана сума = сума до заміру + баланси нових гаманців |
| Аномалії (дублі, невдалі публікації) | Prometheus, `increase()` | Наближені: Prometheus екстраполює лічильники |

### Що зберігається
`summary.csv` — дані для таблиць і графіків роботи. HTML-звіти Gatling і логи лежать у теці кожного прогону, а
в git не потрапляють (великі за розміром). У кожному рядку записано коміт; позначка `-dirty` означає, що код
містив незакомічені зміни, і такий прогін **не можна використовувати** як результат.

## Наслідки
- Один прогін триває приблизно `durationSec` + 2,5 хв на перезапуск, розігрів і злив.
- Для кожної конфігурації потрібно щонайменше 3 повтори; у роботі наводимо медіану та розкид.
- Усі сервіси й навантаження працюють на одному MacBook. Абсолютні значення залежать від машини,
  тому висновки формулюємо через **відносну** різницю між стратегіями в однакових умовах.
