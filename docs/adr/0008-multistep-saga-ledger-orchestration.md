# ADR-0008: Багатокрокова сага з Ledger Service: choreography проти orchestration

- Статус: Прийнято
- Дата: 2026-11-23

## Контекст
Друга вісь порівняння (ADR-0002) — хто координує кроки саги. У поточній системі сага має фактично один крок:
Wallet Service списує й зараховує кошти в одній локальній транзакції. Компенсувати немає чого, і orchestration від
choreography відрізнялася б лише назвами повідомлень. Щоб порівняння мало сенс, потрібні:
- кілька учасників, кожен зі своєю БД;
- крок, який може відхилити вже розпочатий переказ;
- компенсація, що відкочує попередній крок.

## Рішення

### Бізнес-процес: резервування → проведення → завершення
Модель «авторизація і списання», як у картковому процесингу:
1. **Transaction Service** створює переказ зі статусом `PENDING`.
2. **Wallet Service** резервує кошти: списує суму з гаманця-джерела і створює запис утримання (hold) зі статусом `HELD`.
   Якщо коштів не вистачає, гаманця немає або не збігається валюта, переказ одразу відхиляється.
3. **Ledger Service** (новий) перевіряє ліміт на одну операцію і проводить переказ у журналі подвійного запису: дебет
   джерела, кредит отримувача. Якщо сума перевищує ліміт, переказ відхиляється з причиною `LIMIT_EXCEEDED`.
4. **Wallet Service** завершує крок:
   - якщо Ledger схвалив, зараховує кошти отримувачу (hold → `CAPTURED`);
   - якщо Ledger відхилив, повертає кошти джерелу (hold → `RELEASED`). Це **компенсація**.
5. **Transaction Service** ставить `COMPLETED` або `FAILED`.

Компенсація не може сама зазнати невдачі: кошти вже утримані, тож повернення лише додає їх до балансу джерела. Тому
модель «утримання → завершення» обрано замість «списали з одного, зарахували іншому, а потім відкотили» — у другому
варіанті отримувач міг би встигнути витратити гроші, і відкат став би неможливим.

Ліміт задає `payflow.ledger.max-transfer-amount`. У навантажувальному тесті суми рівномірні від 1 до 10, а ліміт 9,
тож приблизно кожен десятий переказ проходить через компенсацію. Правило детерміноване, тому звірка може перевірити,
чи правильне рішення ухвалено для кожного переказу.

### Дві реалізації координації над одними й тими самими локальними транзакціями
Доменні операції спільні для обох стилів: `reserve`, `capture`, `release` у Wallet і `record` у Ledger. Кожна
виконується в одній локальній транзакції разом із позначкою ідемпотентності та подією у outbox. Стилі відрізняються
лише тим, хто вирішує, який крок наступний. Перемикач — `payflow.saga.coordination` (`choreography` | `orchestration`),
однаковий для всіх сервісів.

**Choreography** — сервіси реагують на події один одного:

| Подія | Хто публікує | Хто слухає |
|---|---|---|
| `TransferRequested` | Transaction | Wallet → reserve |
| `FundsReserved` | Wallet | Ledger → record |
| `LedgerApproved` / `LedgerRejected` | Ledger | Wallet → capture / release |
| `TransferCompleted` / `TransferFailed` | Wallet | Transaction → фінальний статус |

Успішний переказ — **4 повідомлення**. Логіку процесу розподілено між трьома сервісами: щоб зрозуміти, де переказ
зараз, треба дивитися в усі три БД.

**Orchestration** — оркестратор у Transaction Service надсилає команди і чекає відповідей:

| Крок оркестратора | Команда | Відповідь |
|---|---|---|
| `RESERVING` | `ReserveFunds` → Wallet | `FundsReserved` / `ReservationFailed` |
| `POSTING` | `RecordTransfer` → Ledger | `LedgerApproved` / `LedgerRejected` |
| `CAPTURING` / `RELEASING` | `CaptureFunds` / `ReleaseFunds` → Wallet | `FundsCaptured` / `FundsReleased` |

Успішний переказ — **6 повідомлень**. Стан саги (`step`) зберігається в таблиці переказів Transaction Service. Кожна
відповідь обробляється в одній локальній транзакції: оновлення кроку + наступна команда в outbox. Тому падіння
оркестратора не губить сагу: після перезапуску outbox дошле команду. Відповідь, що не відповідає поточному кроку
(дубль або запізніла), ігнорується.

Учасники в orchestration не знають один про одного: Wallet і Ledger лише виконують команди. У choreography Wallet
мусить знати про рішення Ledger.

### Доставка подій
Усі повідомлення йдуть через спільний `EventPublisher` з двома реалізаціями: `naive` і `outbox` (ADR-0003, ADR-0004).
Основна серія для другої осі використовує `outbox`, бо перша вісь показала, що naive не гарантує доставку. Naive
лишається доступним, щоб показати, що проблема подвійного запису в багатокроковій сазі не зникає.

### Звірка трьох сервісів
`applied_transfers` у Wallet замінено таблицею утримань `transfer_holds` (`HELD`, `CAPTURED`, `RELEASED`, `REJECTED`).
Ledger зберігає рішення (`ledger_transfers`) і проведення (`ledger_entries`). Аудитор (ADR-0006) зіставляє три БД:
- **узгоджено:** `COMPLETED` + `CAPTURED` + `APPROVED`, або `FAILED` + `REJECTED` у Wallet, або `FAILED` + `RELEASED` +
  `REJECTED` у Ledger;
- **кошти заморожені:** утримання `HELD` після зливу — сага зупинилась посередині, гроші списано, але не зараховано й не
  повернуто;
- **втрачено результат:** Wallet завершив крок, а переказ досі `PENDING`;
- **порушення компенсації:** `CAPTURED` при відхиленні Ledger або `RELEASED` при схваленні — неможливо за дизайном.

Інваріант грошей змінюється: сума балансів **плюс** сума утримань у статусі `HELD` дорівнює початковій сумі.

### Метрики порівняння
- наскрізна затримка саги окремо для успішних і компенсованих переказів;
- кількість повідомлень на переказ (з лічильників опублікованих подій);
- кількість розбіжностей і заморожених утримань після відмов кожного з трьох сервісів, зокрема оркестратора.

## Наслідки
- Попередня серія `series-20261112` (одна вісь, двосервісна сага) лишається відтворюваною з коміту `e5d0573`. Нова
  система порівнює вже багатокрокову сагу, тож числа двох серій напряму не порівнюються.
- З'являється третій сервіс і третя БД (`ledger_db`); у Docker Compose — ще один контейнер з такими самими лімітами.
- Ціна orchestration очікується в затримці (6 переходів через outbox замість 4). Перевага — явний стан саги і менша
  зв'язаність учасників. Це гіпотеза для перевірки, а не результат.
