# Нотатки для тексту роботи і презентації

Сюди записуємо ідеї, щойно вони з'являються: формулювання, ризики, питання до наукового керівника.
**Сюди потрапляють лише цифри з реальних прогонів**, кожна з датою, комітом і описом середовища.

## Питання до наукового керівника
- Погодити розділення на дві осі порівняння і naive dual-write як baseline (ADR-0002).

## Метрики для експерименту (вже є в коді)
| Метрика (Prometheus) | Сервіс | Що показує |
|---|---|---|
| `payflow_transfers_requested_total{strategy}` | transaction | Скільки переказів прийнято |
| `payflow_transfers_e2e_seconds{strategy,outcome}` | transaction | Наскрізна затримка саги: від створення до кінцевого статусу (гістограма, p50/p95/p99) |
| `payflow_transfers_duplicate_results_total` | transaction | Повторні або запізнілі результати, які було проігноровано |
| `payflow_wallet_transfers_processed_total{outcome}` | wallet | Оброблені запити на переказ |
| `payflow_wallet_duplicates_skipped_total` | wallet | Дублі, відсічені idempotent consumer |
| `payflow_events_publish_failed_total` | обидва | Події, які не вдалося надіслати (лише naive) |
| `http_server_requests_seconds` | обидва | Затримка HTTP API |
| `payflow_outbox_lag_seconds` | обидва (outbox) | Від запису події в outbox до підтвердження брокером |
| `payflow_outbox_pending` | обидва (outbox) | Скільки подій чекає на публікацію (росте, коли Kafka недоступна) |
| `payflow_outbox_relay_failures_total` | обидва (outbox) | Невдалі цикли relay (пакет буде надіслано повторно) |

Важливо: затримка `POST /transfers` (HTTP) і наскрізна затримка саги — **різні величини**. Для порівняння
стратегій головна друга, бо outbox додає затримку саме між commit і публікацією.

## Кількісні показники коректності (рахувати після кожного прогону)
- Сума балансів до і після (`GET /api/v1/wallets/total-balance`) — інваріант.
- Перекази, що «зависли» в `PENDING` довше N секунд, — втрачені події.
- Розбіжності між сервісами: переказ `PENDING`/`FAILED`, хоча баланси змінено (потребує звірки — це майбутній Ledger
  або SQL-скрипт reconciliation).

## Справедливість порівняння naive і outbox (сказати в роботі)
- `naive` надсилає подію асинхронно і **не чекає** підтвердження брокера. Outbox-relay чекає на `acks=all`.
  Тому затримка HTTP `POST /transfers` у naive не включає Kafka взагалі, а в outbox — включає лише INSERT в outbox.
  Коректна метрика для порівняння — наскрізна затримка саги `payflow_transfers_e2e_seconds`.
- Інтервал опитування outbox (`payflow.outbox.poll-interval`) — незалежна змінна. Варто зробити прогони щонайменше
  з двома значеннями (наприклад, 10 мс і 100 мс), щоб показати компроміс «затримка ↔ навантаження на БД».
- Гіпотеза для перевірки (не результат!): внесок outbox у затримку саги ≈ один інтервал опитування.

## Методологічні спостереження
- **Повна методика прогону** — в ADR-0005: відкрита модель навантаження, однакові ліміти контейнерів, ізоляція,
  розігрів, злив, джерела кожної метрики.
- **Точність наскрізної затримки** обмежена кошиками гістограми Micrometer. Для p99 це прийнятно, але в роботі це
  треба назвати як джерело похибки (на відміну від HTTP-затримок Gatling, які точні).
- **Пропускна здатність у Gatling** усереднюється разом із 10-секундною фазою наростання, тому вона нижча за цільову.
  Для таблиць краще брати цільову інтенсивність і перевіряти, що система її витримала (нуль помилок, нуль `PENDING`).
- **Розігрів.** Після старту сервісів на свіжому брокері consumer-групи підключаються кілька секунд: Kafka в цей
  час створює `__consumer_offsets`. Перші перекази в такому прогоні чекали значно довше. Перед кожним заміром
  потрібен розігрів, а перші N секунд не враховуються.
- **Ізоляція прогонів.** Між прогонами треба очищати і БД, і топіки (або перестворювати compose-стек). Інакше
  непрочитані події попереднього прогону потрапляють у наступний.
- **Конфлікти оптимістичного блокування.** Конфлікти справді виникають: у тесті з 200 конкурентних переказів між
  5 гаманцями їх було кілька, і повторні спроби їх обробили. Кількість конфліктів — потенційна додаткова метрика.
